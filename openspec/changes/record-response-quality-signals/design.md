# Design

## Context

See proposal.md for why. What the code does today:

- Every upstream call becomes one `Entry` (`src/ledger.rs`): target, provider, model, tokens, cost, outcome (`ok`, `error`, `cancelled`), the missing-usage marker, and the `request_id` that joins it to the decision. Buffered calls are measured when they return (`Metered::call`); streamed answers are measured by a tap (`CallContext::tap`) whose `StreamRecorder` writes the entry when the stream ends or is dropped.
- The tap already sees every normalized chunk (`LlmResponseChunk`): text and reasoning deltas, `ToolCallDelta` (index, id, name, a fragment of the arguments), `Usage`, `MessageStop { reason }` with the provider's own stop string, and `StreamError` / `DecodeError`. It counts generated bytes and notes whether a terminal chunk or a failure arrived, and uses them only for the usage estimate and the outcome. A client that disconnects drops the tap, which submits the entry as `cancelled`, so the two ways a stream can end early are already distinguishable.
- A buffered answer is an `LlmResponse::Agg` carrying content blocks, a normalized `StopReason` (`EndTurn`, `MaxTokens`, `ToolUse`, ...) and usage.
- The decision row is written when the response starts (for a stream, at its headers), before the stream ends. The usage row for that answer is written later and joins to the decision by `request_id`; statistics already read the usage rows (cache ratios) beside the decisions (`src/ledger/stats.rs`).
- `usage` is never pruned; `decisions` are, by `decision_retention_days`. A new column has meant a nullable `ALTER TABLE ... ADD COLUMN`, a `user_version` bump and a migration that runs on a one-connection pool before the real pool opens (the v12 fix, #207).
- In-force ADRs that bound this: 0004 (nothing secret or request-derived in the ledger or logs), 0013 (a decision holds metadata, never prompts or responses), 0016 (metrics use fixed label values), 0028 (the narrow exception for a provider's scrubbed error text), 0029 (the gateway changes conversation content only for invalid tool-call arguments, which is unrelated here).

## Goals / Non-Goals

**Goals:** state four facts about each answer without keeping any of its content; keep them per call, attributed to the target that produced the answer, for as long as the usage row lives, so a later formula can be replayed over history; make them visible on the surfaces operators already use; cost nothing on the response path.

**Non-Goals:** using the flags to route or to change `quality` (later stages, below); judging whether an answer is right; grouping by task class; attributing a bad tool call that shows up in a later request's history to the target that wrote it; per-provider tuning of what counts as a fault; recording the facts for judge calls.

## Decisions

### 1. The flags live on the usage row, not on the decision

The answer's facts are known when its stream ends, after the decision is written. The usage entry is the record written at that moment, it already names the target, provider and model, it joins to the decision by `request_id`, and it is never pruned, which the replay in the later stages needs. Four nullable integer columns are added to `usage` (ledger schema v13), one per signal: `0` unset, `1` set, `NULL` unknown (older rows, judge calls, a call that was not observed). The decision endpoints read the served call's row and show the names of the set flags.

*Alternative:* a field on the decision's attempts JSON. Rejected: the attempts list is complete when the headers are sent, so a streamed answer's flags would need a second write to a JSON blob, and decisions are pruned.
*Alternative:* a new table of events. Rejected: one row per call already exists, and a join for four booleans buys nothing; a table can come later if signals multiply.
*Alternative:* one bitmask column. Rejected: `SUM(col)` per target is the query that matters, and four columns read plainly in SQL and in the schema. A fifth signal (the session attribution) is one more column.
*Alternative:* counters only (Prometheus). Rejected: a counter cannot be replayed against a new formula, which is the point of keeping the facts.

### 2. A pure judge, fed by the tap and the buffered path

A small pure module takes what the response showed and returns the four flags: whether any text appeared, whether any tool call appeared, the stop reason, whether the stream ended normally or failed, and the tool calls' names and accumulated arguments. It does no I/O and cannot panic. The tap feeds it as chunks pass and calls it in `submit()`; the buffered path calls it with the aggregated response. Keeping it pure makes each rule testable with a table, and one rule set serves both paths.

How each flag is decided:

- `empty_output`: finished normally (terminal chunk, or a buffered answer without an error stop) and no text delta and no tool call. A response that held reasoning only is still empty, because the client receives no answer.
- `truncated_output`: the stop reason is a length stop. Buffered: `StopReason::MaxTokens`. Streamed: the provider's stop string (`length`, `max_tokens`, `max_output_tokens`), matched case-insensitively. An unknown string sets nothing.
- `bad_tool_call`: any tool call with an empty or missing name, or arguments that are not blank and do not parse as a JSON object. The test is the repair's own (`repair::tool_arguments` returns `Some` for text that is not an object), with blank text excluded, because providers send blank arguments for a tool that takes none. The rule therefore agrees with the repair: what 0.19.0 would repair in a later request is what is flagged here.
- `cut_stream`: the loop over the provider's stream ended, or failed, without a `MessageStop`. A tap that is dropped by a client disconnect never reaches the end of the loop, so it does not set `cut_stream`; this keeps a user closing the terminal from being scored against a model.

*Alternative:* judge in `server.rs` from the final response. Rejected: a stream's body never reaches the handler as a whole; the tap is the only place that sees it.

### 3. Bounded accumulation for tool-call arguments

Arguments arrive as fragments per tool-call index. The tap keeps, per index, the name and the concatenated fragments, up to 16 calls and 64 KiB per call; the judge runs once at the end. A call past either bound is not judged (its flag stays unset), so a runaway argument cannot grow memory or cost a parse, and the bound is a statement that the flag is only set when it was actually looked at. The memory is released with the recorder. The tap already forwards each chunk untouched; the accumulation reads a borrowed chunk and never modifies or holds up `yield item`.

*Alternative:* parse incrementally per fragment. Rejected: more code and state for a flag that only needs the final text.
*Alternative:* an unbounded buffer. Rejected: the response size is the provider's, not ours.

### 4. Stored as the entry is finalized, shown by join

`Entry` gains the four values. `StreamRecorder::submit()` and the buffered finalize set them; `Accounting::complete()` counts them in `Metrics` (decision 6) and queues the entry as today. The decision endpoints add the served call's flags by reading the usage row with `request_id` and `kind = 'answer'`; when the row is not there yet (the stream is still open) the decision is returned without them.

### 5. Statistics report counts, not a derived score

Per group, the statistics return `observed` (answer calls with known signals) and one count per signal; the consumer divides. A computed score belongs to a later stage and a formula we have not chosen. Calls with unknown signals are in neither figure, so the pre-v13 history does not look like perfect answers.

### 6. Metrics: two counters, fixed labels

`humpyard_response_calls_observed_total{route,target}` and `humpyard_response_signals_total{route,target,signal}` with `signal` from the four-name set. Route and target use the existing bounded vocabulary (ADR 0016). No key label.

### 7. Where the work goes after this change

Recorded here so the schema and the definitions are chosen with them in mind; each is its own change:

1. **Attribute a bad tool call found in a later request's history to the target that wrote it**, through the session: the repair already counts them, and the previous served target in that session is on the decision. A fifth column, `poisoned_history`, on the usage row of the call that carried the bad history, or a lookup at read time; to be decided there.
2. **A shadow "effective quality"**: computed from the flags per target (a smoothed rate against the declared `quality` as the prior, with a minimum sample count), shown beside the declared value in the configuration view and the statistics, never used by routing. Replayed over the stored history before anyone trusts it.
3. **Applied to routing**, bounded (a fixed maximum distance from the declared value), decaying so a target that failed once is looked at again, with a per-target freeze and one global off switch, and the applied value recorded on the decision.

## Risks / Trade-offs

- **A client sets a low `max_tokens`.** Then a length stop is the client's doing, not the model's. → The flag states the fact and nothing else; the request's output limit is not recorded in this change. If the later stages show it distorting rates, record whether the request set a limit (a boolean, not the value) and divide by it.
- **A provider names its stop reasons differently.** → A table of known strings, case-insensitive, and anything unknown sets nothing; a missing flag is a quiet undercount, not a wrong score.
- **Blank arguments hide a real fault.** A model that emits a tool call with blank arguments for a tool that needs some is not flagged. → Accepted; the repair also treats blank as `{}` and the call fails at the client, where it shows as a failed tool run.
- **Reasoning-only answers are counted empty.** A model that thinks and then runs out of budget is empty and truncated at once. → Both flags are true facts; the stages that use them can weigh the pair.
- **Streams the provider ends early on purpose.** Some providers close without a terminal chunk. → `cut_stream` is a fact about the stream; a provider that always does this will show a rate of 1, which is itself the signal to treat it differently.
- **Four columns on a table that is never pruned.** → Four small integers per row; the table's growth is already tracked as a ledger-scale item in the roadmap.
- **Schema v13 is one-way.** → Back up the ledger before upgrading, as for v12.

## Migration Plan

1. Ship v13 as an additive step on the one-connection pool, before the real pool opens, like v12. Rows already in the table read as unknown.
2. Deploy; no configuration changes. The flags start filling for new calls; the statistics report `observed` counts that grow from zero.
3. Roll back by running the previous version against the migrated file: the extra nullable columns are ignored (as v12's were) and nothing in the flags is read by routing.

## Open Questions

- Whether the admin API's per-target statistics should also return the rate, or only the counts. The counts are the contract here; a rate can be added without changing anything stored.
